# The field renderer

`lib/field/` turns a scene described in football terms — yards across from
the middle of the field, yards from a reference line — into an SVG field:
turf, sidelines, yard lines and their numbers, hash marks, the end zone, the
uprights, the players and officials on it. Nothing outside this directory
should contain a raw coordinate or a copy of what a mark looks like; if
something needs to be drawn that this module can't express yet, the fix is to
extend the module, not to work around it at the call site.

**Current consumer: `/draw`.** The drawing page (`docs/draw/README.md`)
builds its board entirely from `renderField()`, `STYLE`, `DEFS` and `views` —
see `lib/draw/board.js`. The 50 hand-committed SVGs under `static/images/`
are not (yet) generated by this renderer; replacing them with output from it
is the remaining work of
`docs/superpowers/plans/2026-08-27-field-diagrams-svg.md` (Tasks 2 onward —
this renderer's `geometry.js`, `field.js`, `style.js` and `views.js` are that
plan's Task 1, and `markers.js` was built here, under the drawing-tool plan,
to that plan's own stated interface, so the diagrams plan finds it already
done and already proved by a second consumer when it resumes). Once that
migration lands, this file should be updated to say so and to describe
whatever "add a diagram" workflow it introduces — there isn't one today, only
a renderer and one real caller.

## The modules

- **`geometry.js`** — the coordinate system, and the only place a yard
  becomes an SVG unit or the reverse. See the table below.
- **`style.js`** — the one stylesheet (`STYLE`) and the shared `<defs>`
  (`DEFS`, the end-zone hatch pattern and the arrowhead marker) every field
  inlines. Three drifted copies of this existed across the diagrams this
  renderer is meant to replace; this is the fix.
- **`field.js`** — `renderField(view)`: the field itself — turf, lines,
  hashes, numbers, end zone, uprights, the press-box legend. No players and
  no officials; those are `markers.js`, kept separate so the field renderer
  (which draws everything at an absolute football coordinate) and the
  drawing page (which drags one token at a time) can share one
  implementation of every shape instead of each growing its own.
- **`markers.js`** — everything that goes *on* a field: `official()`,
  `player()`, `movement()` (an arrow), `note()`, `flag()`, and `label()` (a
  user-written caption, the one mark whose look isn't fixed by `STYLE`).
- **`views.js`** — the named crops (`spot`, `runPass`, `goalLine`,
  `fieldGoal`, `punt`, `kickoff`): how much field is in frame, how hard it's
  squashed lengthwise, and which lines are drawn. `geometry.js` explains what
  each view field means.
- **`escape.js`** — `escapeText()`, the one escaper every string that reaches
  markup goes through. It escapes quotes as well as `&`/`<`/`>`, because a
  string that starts as element text (a caption) can end up inside an
  attribute value too (`label()`'s `color`), and nothing downstream can
  assume otherwise.

## The coordinate system

Two independent scales, because they have to be:

- **Across the field, the scale is fixed.** Every field is 270 SVG units
  wide with the sidelines 200 units apart, so a yard is always 3.75 units
  (`UNITS_PER_YARD_X`, derived from `FIELD_WIDTH_YARDS` — NFHS 1-2-1, the
  field is 160 feet wide — and the sideline positions, not written as its own
  decimal, so the two can't drift apart).
- **Along the field, each view picks its own `scaleY`.** A view showing three
  yards either side of a goal line and one showing a 70-yard kickoff cannot
  share a scale and both fit in a reasonable viewBox. This is why a field
  looks stretched lengthwise compared to across it — that is the point, not a
  bug.

| Constant | Value | Source |
| --- | --- | --- |
| `VIEWBOX_WIDTH` | 270 | Every field is this wide; the margins hold out-of-bounds officials (wings work the sideline from outside it). |
| `SIDELINE_LEFT` / `SIDELINE_RIGHT` | 35 / 235 | Measured off the diagrams this renderer replaces. |
| `FIELD_WIDTH_YARDS` | 160⁄3 ≈ 53.33 | NFHS 1-2-1: the field is 160 feet wide. |
| `UNITS_PER_YARD_X` | 3.75 | `(SIDELINE_RIGHT − SIDELINE_LEFT) / FIELD_WIDTH_YARDS` — derived, not written down, so the sidelines and hash marks can't drift apart. |
| `HASH_FROM_SIDELINE_YARDS` | 160⁄9 ≈ 17.78 | NFHS 1-2-1: hash marks are 53'4" in from each sideline. |
| `GOAL_POST_SPACING_YARDS` | 70⁄9 ≈ 7.78 | NFHS 1-2-4: the uprights are 23'4" apart. |
| `HASH_PITCH_YARDS` | 5 | Hash marks are drawn every five yards, not every yard — at diagram scale a one-yard pitch reads as a solid line and prints as a smear. |

`x(yardsFromCentre)` and `y(view, yards)` convert football units to SVG units
for drawing; `xToYards(svgX)` and `yToYards(view, svgY)` are the exact
inverses, used by the drawing page to turn a pointer position back into a
yard. Both directions live here, beside each other, rather than the inverse
being worked out again at a call site with its own copy of
`UNITS_PER_YARD_X` and a view's `scaleY` in it.

## Monochrome, by constraint

Every field these modules draw is black-and-white — `style.js` is explicit
about why: these get printed on whatever laser an association has and
photocopied, so a gray fill dithers badly and is avoided (the end zone is
hatched, not filled), and the officials are told apart by shape — solid disc,
outlined disc, halo — rather than by colour. This rule is inherited by every
consumer. `/draw` is the one exception, and a narrow one: a user's own
caption text may be coloured, because that is a feature asked for, and it
comes with the print-legibility warning stated once on that page — see
`docs/draw/README.md`.

## Pure by requirement, not by convention

Nothing in this directory touches `document`, imports a `node:` built-in, or
reads a global beyond plain JavaScript. That is a real constraint, not a
style choice: `lib/field/` is passthrough-copied to `/js/field/`
(`.eleventy.js`) so `/draw` can import these exact files in a browser, and a
relative import such as `./geometry.js` has to resolve the same way whether
`node --test` is running it or a `<script type="module">` is. A module here
that reached for `node:fs` or `window` would work in tests and silently break
in the browser, or the reverse — there is no test that would catch it, only
the build. See `docs/draw/README.md` for the rest of that mirroring rule.

## Tests

```bash
node --test "test/field/*.test.js"     # or: npm run test:field
```

`geometry.test.js` and `markers.test.js` assert structure and placement —
which classes, how many, where a coordinate lands — not pixels: a marker
drawing the right shape in the wrong spot is a `geometry.js` bug, and a wrong
class or count is a `markers.js` one.
